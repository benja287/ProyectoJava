--------------------------------------------------------------------------------
QUÉ EVALÚA LA ENTREGA 4
--------------------------------------------------------------------------------
  • API REST con Jersey + CDI + Swagger
  • Endpoints por rol (Admin, OC, Evaluador, Autor, Participante)
  • Persistencia en MySQL (jyaa2026_bd1)
  • Archivos PDF en filesystem (trabajos y comprobantes de pago)

QUÉ NO ES OBLIGATORIO PROBAR AHORA
  El flujo completo del congreso (registro → pago → esperar aprobación admin →
  participar → enviar trabajo → ganar rol autor) es del sistema completo, no del
  alcance mínimo de esta entrega.

  En la entrega 4 probamos que cada rol tiene sus endpoints y que persisten
  en la base.


--------------------------------------------------------------------------------
CÓMO FUNCIONA EL LOGIN EN NUESTRA API
--------------------------------------------------------------------------------
  POST /api/login valida email/password y devuelve el usuario (UsuarioDTO).

  No hay token JWT: Swagger no bloquea endpoints por rol. Vos simulás el rol
  sabiendo qué endpoints le corresponden a cada uno.

  En el coloquio: "como administrador haría X…", "como OC haría Y…", etc.


--------------------------------------------------------------------------------
CÓMO USAR SWAGGER (siempre igual)
--------------------------------------------------------------------------------
  1) Abrís la sección del endpoint (ej. Health, Usuarios, Login…)
  2) Clic en "Try it out"
  3) Completás parámetros y/o Request body
  4) Clic en "Execute"
  5) Mirás Server response → Code y Response body
  6) (Opcional) Verificás en phpMyAdmin que la fila quedó en MySQL


--------------------------------------------------------------------------------
FORMATOS DE RESPUESTA (DTOs) — ACTUALIZADO POST-COLOQUIO
--------------------------------------------------------------------------------
  Para evitar JSON circular, lento y con datos sensibles (password), varios
  endpoints ya NO devuelven la entidad JPA cruda. Devuelven DTOs:

  TRABAJOS
    GET  /api/trabajos              → PaginaTrabajosDTO (items + page + total)
    GET  /api/trabajos?autorId=245   → PaginaTrabajosDTO filtrado por autor
    GET  /api/trabajos/{id}         → TrabajoResumenDTO
    POST /api/trabajos              → TrabajoResumenDTO (201)
    PUT  /api/trabajos/{id}/enviar  → TrabajoResumenDTO
    POST /api/trabajos/{id}/documento → TrabajoResumenDTO

  Parámetros paginación trabajos: page (default 1), size (default 20, máx 100)

  ACTIVIDADES
    GET  /api/actividades           → PaginaActividadesDTO (items + page + total)
    GET  /api/actividades/{id}      → ActividadResumenDTO
    POST /api/actividades           → ActividadResumenDTO (201)
    PUT  /api/actividades/{id}      → ActividadResumenDTO

  Parámetros paginación actividades: page (default 1), size (default 20, máx 100)

  CRONOGRAMA
    GET  /api/cronograma/{usuarioId} → CronogramaDTO
    POST /api/cronograma/.../actividades/{id} → CronogramaDTO

  ASIGNACIONES EVALUACIÓN
    POST /api/asignaciones-evaluacion → AsignacionEvaluacionDTO (201)
    PUT  /api/asignaciones-evaluacion/{id}/respuesta → AsignacionEvaluacionDTO

  USUARIOS
    GET  /api/usuarios              → PaginaUsuariosDTO (items + page + total)
    GET/POST/PUT /api/usuarios/{id} → UsuarioDTO (sin password)

  Parámetros paginación usuarios: page (default 1), size (default 20, máx 100)

  PAGOS
    GET  /api/pagos/pendientes      → PaginaPagosDTO (items + page + total)
    GET/POST/PUT pagos individuales → Pago (entidad plana, sin ciclo JSON)

  Parámetros paginación pagos pendientes: page (default 1), size (default 20, máx 100)

  CIRCULARES
    GET  /api/circulares            → PaginaCircularesDTO (items + page + total)

  Parámetros paginación circulares: page (default 1), size (default 20, máx 100)

--- GESTIÓN DE PAGOS — Validar pagos pendientes ---

Requisitos PDF: aprobar/rechazar, motivo de rechazo, ajuste de monto.
Tabla: pagos (estado, motivo_rechazo, monto) + inscripciones_congreso
Estados: PENDIENTE, APROBADO, RECHAZADO
Métodos: TRANSFERENCIA, TARJETA, EFECTIVO

0. Preparación — Registrar pago pendiente

  {
    "usuarioId": 243,
    "pago": {
      "monto": 5000,
      "metodo": "TRANSFERENCIA",
      "requiereFactura": false
    }
  }
  Code: 201 | estado: PENDIENTE | id ej. 55 | header Location

  Descargar PDF:
    Navegador: https://grupo1.jyaa-ci.linti.unlp.edu.ar/api/archivos/comprobantes/NOMBRE.pdf
    Swagger Archivos → GET /api/archivos/{carpeta}/{nombre}
      carpeta=comprobantes, nombre=comprobantes-uuid.pdf → Code 200

  Dónde se guarda el PDF:
    Bytes → filesystem Tomcat: $CATALINA_BASE/uploads/grupo1/comprobantes/
    MySQL → solo comprobante_url (NO BLOB)

1. GET /api/pagos/pendientes → Code 200
   Response body (PaginaPagosDTO): items[] con el pago 55 PENDIENTE, page, total, totalPages

  Code: 200 | estado: APROBADO | mensaje: "Pago aprobado"

NOTAS PARA EL COLOQUIO

DTOs y paginación (mejora post-coloquio):
  Listados grandes (trabajos, actividades) usan paginación + DTO resumido.
  Cronograma, asignaciones y detalle de trabajos usan DTOs sin relaciones
  circulares. Así Swagger responde rápido y sin "can't parse JSON".

PDFs (trabajos y comprobantes):
  MySQL guarda solo la URL. El binario está en filesystem Tomcat.
  Descarga: GET /api/archivos/{carpeta}/{nombre}

Sin JWT:
  No hay bloqueo por rol en Swagger. Simulamos rol por contexto del coloquio.

Persistencia:
  Cada POST/PUT exitoso debe verse en phpMyAdmin (jyaa2026_bd1).
