Entrega 2 · La pregunta clave

¿Cuál es nuestro diseño?

modelo de objetos del dominio

Diseñamos el congreso como objetos Java del negocio (POJOs): cada cosa importante es una clase con datos, estado y relaciones. Ese diseño no guarda nada en MySQL todavía — solo dice qué existe.

Ejemplo concreto

Trabajo

titulo, resumen, estado, PDF… métodos como enviar().

AsignacionEvaluacion

¿este evaluador aceptó revisar este trabajo?

Evaluacion

el dictamen: aprobar / rechazar + comentario.

Lo mismo para Usuario, Pago, InscripcionCongreso, Actividad… Más adelante mostramos ese diseño en el diagrama completo.

Qué problema deja planteado

Cuando el servidor se apaga, esos objetos en memoria se pierden.

Hace falta persistencia: copiar cada objeto a una fila de MySQL y volver a armarlo después.

Pregunta de diseño: ¿quién se ocupa de guardar y buscar? Si lo metemos en Trabajo o en el servlet, mezclamos el negocio con MySQL.

Por eso elegimos el patrón DAO: una responsabilidad aparte (acceso a datos de una entidad). Siguiente: por qué ese camino.

Entrega 2 · qué es el modelo
Entrega 2 → 3 · El camino

Por qué fuimos por DAOs

separar “el negocio” de “la base”

El modelo de objetos ya estaba partido en entidades claras (Usuario, Trabajo…). Eso nos empujó a un camino simple: una entidad del diagrama → una tabla → un DAO.

Camino que evitamos

La alternativa era escribir el código que habla con MySQL (EntityManager, consultas) directamente adentro de la clase Usuario o del servlet que atiende el pedido HTTP. Esto genera varios problemas:

  • Usuario pasaría a depender de cómo está armada la base de datos: si mañana cambia algo en MySQL, hay que modificar la clase que define las reglas del usuario, aunque esas reglas no tengan nada que ver con la base.
  • Si diez pantallas distintas necesitan guardar o buscar un usuario, la misma lógica de persist/find quedaría copiada diez veces, en vez de estar en un solo lugar.
  • Se vuelve imposible probar que las reglas del negocio funcionan bien sin tener la base de datos levantada y conectada, porque quedan mezcladas en el mismo código.

En resumen, esta alternativa mezcla dos responsabilidades que deberían estar separadas: las reglas propias del congreso y la comunicación con MySQL.

Camino que elegimos: DAO

DAO = Data Access Object: es un patrón de diseño (no “magia de JPA”). En el código es una clase —o interfaz + implementación— cuya única responsabilidad es el acceso a datos de una entidad: guardar / buscar / actualizar / borrar.

  • Usuario = datos y reglas del usuario (modelo E2).
  • UsuarioDAO + UsuarioDAOImpl = cómo entra y sale de MySQL (E3).
  • JPA (@Entity, EntityManager) = la herramienta que usa el DAO para mapear objeto ↔ fila.

Por eso el modelo nos llevó a DAOs: ya teníamos objetos bien cortados; el DAO es el “portero” de cada uno hacia la base, sin ensuciar el diagrama de negocio.

Con el DAO ya separamos dominio e infraestructura. En la E3 el Servlet todavía hace de puerta HTTP y, a la vez, coordina el caso de uso. En la E4 terminamos ese corte: Resource → Service → DAO.

Camino del diseño

HU → clase del diagrama → POJO → entidad JPA → tabla MySQL → DAO (CRUD de esa entidad) → Factory (un solo lugar crea el DAO) → en E4, CDI inyecta esas dependencias.

Del modelo de objetos a datos que no se pierden

rama entrega-3

Venimos de la E2: ya teníamos el diseño del dominio (clases y relaciones). El objetivo de la E3 fue persistirlo: que un Usuario o un Trabajo viva en MySQL y sobreviva al reinicio del servidor.

Qué pedía la entrega

  • Capa de persistencia con JPA sobre MySQL del curso.
  • Patrón DAO con ABM (alta, baja, modificación, recuperación).
  • App web Java desplegable (WAR / Tomcat) y verificable.
Hilo

Antes los datos vivían en el navegador (localStorage). Acá pasan al servidor. Todavía no es la API limpia con CDI (eso es E4). Primero había que demostrar que el modelo se guarda bien.

Para lograr esto necesitamos una app web en Java: un servidor que ejecute la aplicación, herramientas que conecten el modelo con la base, y un patrón que ordene el acceso a los datos. Empecemos por la base: cómo se ejecuta la aplicación (WAR + Tomcat).

Entrega 3 · 1 → conceptos
Entrega 3 · 2/7 · Conceptos Java web

Qué aprendimos a usar

qué hicimos · qué significa

En esta entrega no solo “guardamos datos”: aplicamos ideas centrales del desarrollo web en Java. Cada una responde a una pregunta distinta.

1 · WAR + Tomcat 10 (Jakarta)

La aplicación se empaqueta en un solo archivo desplegable (WAR). Un servidor de aplicaciones —Tomcat— es el encargado de ejecutarlo. Usamos la especificación moderna de Java para la web: Jakarta EE (Tomcat 10), que define cómo se escriben y despliegan este tipo de sistemas.

2 · Ciclo de vida (ServletContextListener)

Una app web no “está siempre prendida” de la misma forma: tiene un ciclo de vida. Al arrancar, se conecta a la base de datos y, si hace falta, carga datos iniciales para poder probar. Al apagar, se cierra todo de forma ordenada para no dejar conexiones ni recursos abiertos.

3 · Servlet

Cada funcionalidad importante tiene un responsable que atiende los pedidos que llegan por una dirección concreta (URL) y devuelve una respuesta según lo pedido: listar, crear, probar la persistencia, etc.

4 · Cliente–servidor + JSON

El cliente (navegador u otra herramienta) pide algo; el servidor responde. Esa respuesta puede ser datos estructurados (JSON), pensados para que otro programa los use, o una página pensada para que la lea una persona (por ejemplo, el resultado de las pruebas de ABM).

5 · Persistencia orientada a objetos

En lugar de escribir a mano instrucciones de base de datos en cada pantalla, trabajamos con objetos del dominio (usuario, trabajo, pago…). Existe una capa intermedia que traduce esos objetos a datos guardados en tablas —y al revés al leerlos.

En una frase: empaquetamos y desplegamos la app → al arrancar queda lista la base → cada URL tiene quién la atiende → cliente y servidor se hablan → los objetos del modelo se persisten sin mezclar eso en cada pantalla.

Entrega 3 · 2 → herramientas
Entrega 3 · 3/7 · Librerías y herramientas

Cómo las usamos, de punta a punta

no solo “cuál” · también “cómo”

No es una lista suelta: es la cadena que lleva lo que programamos hasta la app que corre en el servidor del curso.

Paso A · Armar el producto (Maven)

El código no se puede ejecutar tal cual en un servidor: hay que empaquetarlo en un solo archivo (WAR) con todo lo necesario. Maven arma ese paquete automáticamente: revisa qué librerías necesita la app (Hibernate, MySQL, Gson, Logback…), las descarga, compila y genera el WAR (mvn package → jyaa2026-grupo1.war).

Paso B · Hablar con la base (Hibernate + MySQL)

La app piensa en objetos (usuario, trabajo…); la base guarda tablas. MySQL es el motor que persiste esos datos en disco (jyaa2026_bd1). Hibernate (JPA) es el traductor automático entre ambos mundos: nosotros trabajamos con objetos; él genera el SQL. La configuración vive en persistence.xml.

Paso C · Responder al cliente (Gson + Logback)

El navegador no entiende objetos Java: hace falta un formato universal. Gson los traduce a JSON para que el cliente pueda usarlos. Logback es el “cuaderno de bitácora”: registra qué pasó (incluido el SQL) para detectar errores (logback.xml, consola de Tomcat).

Paso D · Llevarlo al servidor (Docker + GitLab CI)

En el servidor del curso no se instala cada proyecto a mano: se arma una caja (contenedor Docker) con Tomcat y el WAR listos para correr. GitLab CI automatiza ese proceso en un pipeline: cada vez que subimos código, se construye la imagen, se reemplaza el contenedor y Traefik publica la URL del grupo. Referencia: Dockerfile · dominio del curso.

Entrega 3 · 3 → JPA
Entrega 3 · 4/7 · JPA / Hibernate

Cómo el diagrama de la E2 se vuelve tablas

objeto Java ↔ fila MySQL

En la E2 el modelo vivía en memoria. En la E3 Hibernate se encarga de guardarlo y recuperarlo en MySQL, sin que escribamos el SQL a mano en cada pantalla.

¿Qué es una entidad?

En la E2 diseñamos clases Java que representaban cosas del congreso (Trabajo, Usuario), pero eran solo objetos en memoria. Una entidad es esa misma clase, marcada con @Entity, para decirle a Hibernate que debe guardarse en una tabla. El @Id identifica cada fila de forma única (como un DNI). Por ejemplo, Trabajo se convierte en la tabla de trabajos, y la relación con el autor (@ManyToOne) en una columna con el id de ese usuario (autor_id).

Relaciones = flechas del diagrama

El diagrama de la E2 mostraba relaciones (un trabajo tiene muchas evaluaciones, una inscripción un solo pago, etc.). En la base eso son columnas que referencian otra fila. Hibernate necesita el tipo de cada relación: @OneToMany / @ManyToOne (un trabajo, muchas evaluaciones; cada evaluación, un solo trabajo); @OneToOne (una inscripción, un único pago); @ManyToMany (actividad con varios trabajos y viceversa); @ElementCollection (listas simples: roles, coautores); @Enumerated (estados fijos como EstadoTrabajo).

EMF y EntityManager

El EntityManagerFactory (EMF) es la conexión general a la base: se crea una sola vez al arrancar (lo hace JpaUtil) y permanece abierta mientras corre el servidor.

El EntityManager (EM) ejecuta cada operación (guardar, buscar, actualizar, borrar): se abre para esa operación y se cierra apenas termina.

La transacción: si todo sale bien, commit; si falla a mitad, rollback (nada a medias).

Quién abre el EntityManager cada vez: el DAO. Quién lo crea: la Factory.

persistence.xml

Es el archivo donde le decimos a Hibernate cómo y dónde conectarse: qué base, con qué usuario, y qué clases tratar como entidades. En Tomcat hay que listar a mano las ~15 clases: no las descubre solo.

Entrega 3 · 4 → DAO
Entrega 3 · 5/7 · DAO + Factory

Quién guarda en MySQL (y por qué no el Servlet)

patrón DAO · patrón Factory · ABM

Si el Servlet hiciera SQL, mezclaríamos “atender pedidos HTTP” con “hablar con la base”. Por eso cada entidad tiene su DAO, y el Factory es el único lugar que crea esos DAOs.

DAO = Data Access Object (patrón)

El DAO es el “portero” de una sola entidad: el único responsable de guardar, buscar, actualizar o borrar sus datos (por ejemplo, todo lo de un trabajo pasa por TrabajoDAO). No es magia de JPA, sino una decisión de diseño: en código es una interfaz con su implementación (TrabajoDAO / TrabajoDAOImpl).

Cómo lo apilamos

Todas las entidades necesitan las mismas operaciones básicas (guardar, buscar, actualizar, borrar). En vez de repetir esa lógica, se define una sola vez: GenericDAO<T> declara el ABM común, y AbstractJpaDAO lo implementa (abre el EntityManager, arranca la transacción, ejecuta persist / merge / remove / find, y cierra). Cada entidad hereda eso y solo agrega consultas propias (por ejemplo, buscar por email).

Factory

Si cada Servlet o test creara el DAO con new TrabajoDAOImpl(), esa línea se repetiría en muchos archivos y un cambio de implementación obligaría a tocarlos todos. DAOFactory.getTrabajoDAO() centraliza la creación: es un patrón creacional; todos piden el DAO ahí y no les importa cómo está armado por dentro.

Ejemplo completo: guardar un trabajo

  1. Llega un pedido POST /api/trabajos: el Servlet lee el JSON del cliente.
  2. Pide el DAO al Factory con DAOFactory.getTrabajoDAO() (y el de usuario si hace falta).
  3. Arma el objeto Trabajo en memoria: todavía no está en la base.
  4. Llama a trabajoDAO.alta(t): ahí se abre la transacción, se guarda el objeto (persist) y se confirma el cambio (commit).
  5. Hibernate genera el INSERT y MySQL asigna el id.
  6. Gson arma la respuesta 201 con el trabajo ya persistido.

Prueba de la entrega: /test-persistencia ejecuta ~14 ABM (usuario, inscripción y pago, trabajo, asignación y evaluación…) y muestra OK o FALLO. Así respondemos la pregunta de la primera diapositiva: quién guarda y busca es el DAO, no el Servlet ni la clase del negocio. Con eso la E3 demuestra que el modelo ya vive en MySQL; en la siguiente vemos qué nos costó y qué quedó para la E4.

Entrega 3 · 5 → dificultades
Entrega 3 · 6/7 · Dificultades y cierre

Qué nos costó y qué quedó para la E4

de la E3 a la E4
① “Unknown entity” en Tomcat

Hibernate se queja porque no reconoce una clase como entidad, aunque tenga @Entity. A diferencia de otros entornos, Tomcat no escanea el proyecto para descubrirlas solo. Lo resolvimos declarando cada clase a mano con una etiqueta <class> dentro de persistence.xml.

② Lazy loading al listar

Por defecto, algunas relaciones no se traen de la base hasta que se usan. Si se accede a esa colección después de cerrar la sesión, Hibernate falla (could not initialize proxy — no Session). /test-persistencia lo dejó en evidencia: ~13 ABM en OK y un FALLO en Actividad.trabajos (siguiente diapositiva). En el resto lo corregimos con JOIN FETCH en los DAOs; este caso pendiente muestra que la batería de pruebas sirve para detectar huecos reales.

③ Capas mezcladas (límite de la E3)

El Servlet pedía el DAO al Factory y manejaba el acceso a datos él mismo: mezclaba la puerta HTTP con el caso de uso y el acceso a MySQL. Alcanzó para demostrar el ABM, pero no es una API prolija. En la E4 separamos en tres capas — Resource (puerta HTTP), Service (aplicación / caso de uso) y DAO (infraestructura / MySQL) — dejando el dominio (Usuario, Trabajo…) sin HTTP ni SQL. CDI (@Inject) las conecta y Jersey atiende HTTP.

Cierre: en la E3 el modelo se persiste y se despliega; la prueba ABM lo verifica en vivo. En la E4 ordenamos capas con DIP: la web ya no crea DAOs a mano — el contenedor los inyecta.

Entrega 3 · evidencia de persistencia
Entrega 4 · 1/13 · Puente

De la Práctica 6 al problema que resolvimos

rama entrega-4
Lo que ya sabíamos (Práctica 6) — el recorrido
1 · Del cliente a Jersey

El cliente manda un POST con JSON a /api/usuarios. Tomcat recibe el pedido y, como la URL empieza con /api/*, se lo pasa al ServletContainer de Jersey (registrado en web.xml). Jersey todavía no persiste nada: solo enruta según @Path("/usuarios"), @POST, @Consumes y @Produces.

2 · Jackson arma el objeto y se ejecuta alta

El método pide un parámetro Usuario, no un texto. Jersey busca un MessageBodyReader; encuentra el de Jackson, que parsea el JSON y construye el objeto. Recién ahí se ejecuta UsuarioResource.alta(...) con el usuario ya armado.

3 · El Resource le pasa el objeto al DAO

Desde UsuarioResource se recibe el objeto parseado y se lo entrega al DAO. El Resource no sabe SQL, no arma el JSON a mano y no abre la conexión a MySQL: solo atiende HTTP y delega la persistencia.

4 · Hibernate traduce el objeto a un INSERT

Al arrancar, JpaBootstrapListener crea una sola vez la EntityManagerFactory. En cada operación el DAO obtiene un EntityManager y llama a em.persist(usuario). Hibernate lee @Entity y @Table de la clase y arma el INSERT que ejecuta MySQL.

5 · La respuesta vuelve en JSON

El método hace return del resultado. Jersey lee @Produces, busca un MessageBodyWriter y Jackson convierte el objeto otra vez a JSON. El cliente recibe HTTP 200 (o el código que corresponda) con ese body. La Entrega 4 no tira abajo este recorrido: lo extiende.

El problema

En la Práctica 6, UsuarioResource dependía de la clase concreta UsuarioDAOImpl. Si cambiábamos cómo se persiste, había que tocar la capa HTTP. Esa capa no debería saber quién fabrica el DAO ni cómo habla con MySQL.

Qué pedía la E4: separar en capas, que el Resource deje de conocer UsuarioDAOImpl, y que CDI / Weld conecte las piezas con @Inject.

Entrega 4 · 1 → capas
Entrega 4 · 2/13 · Arquitectura

Cuatro capas, una responsabilidad cada una

presentación · servicio · dominio · infraestructura
Presentación

Recibe el pedido HTTP y arma la respuesta (201, 400, JSON). Ejemplo: UsuarioResource. No sabe SQL ni cómo se abre la conexión a la base.

Aplicación / Servicio

Coordina el caso de uso: valida reglas y recién ahí pide guardar o buscar. Ejemplo: UsuarioService (email único, rol por defecto).

Dominio

Qué es cada cosa del negocio: Usuario, Trabajo, estados y roles. Sin HTTP y sin detalles de MySQL.

Infraestructura

Habla con el mundo técnico: la implementación del DAO, Hibernate, MySQL, y el almacenamiento de archivos PDF en disco.

Qué sí y qué no puede saber UsuarioResource

La razón de fondo: cada capa solo conoce a la de al lado, nunca a las de más abajo. El Resource habla con el Service; el Service habla con la interfaz del DAO; la implementación del DAO habla con MySQL. Si el Resource conociera UsuarioDAOImpl, un cambio en cómo se guarda obligaría a tocar la puerta HTTP. Por eso el Resource no “salta” capas.

Sí: que existe UsuarioService, que puede pedirle el alta de un usuario, códigos HTTP, y que el cuerpo del pedido es un usuario o un DTO.

No: que la implementación se llama UsuarioDAOImpl, nombres de tablas, ni cómo se abre o cierra la sesión con la base.

DTOs: entrada y salida

Un DTO (Data Transfer Object) es un objeto pensado solo para viajar por la red: decide exactamente qué datos entran o salen en el mensaje. Si devolvemos la entidad completa del usuario, mandamos de más: la contraseña, y relaciones entre objetos que pueden hacer que la respuesta se enrede en un ciclo infinito. El DTO corta ese problema: controlamos qué viaja en el mensaje.

En el proyecto hay dos casos concretos de esa idea. Entrada: en el login solo hacen falta el email y la contraseña; no hace falta mandar todo el usuario. Salida: cuando respondemos con los datos de un usuario, el mensaje no incluye la contraseña.

A futuro, separar el DTO de la entidad protege el contrato con quien consume la API (Swagger, el frontend, otro cliente). Si el modelo de usuario cambia o crece en próximas entregas, ese cambio queda contenido en el dominio: no se filtra solo al JSON que ya reciben los clientes. Quien decide qué se muestra es el DTO, no la entidad.

Entrega 4 · 2 → DIP
Entrega 4 · 3/13 · DIP

Si el Resource no conoce el DAO concreto, ¿a qué le habla?

la pregunta que quedó abierta
La pregunta que quedó de la diapositiva anterior

Dijimos que UsuarioResource no puede conocer UsuarioDAOImpl ni saltar capas hacia MySQL. Entonces, cuando el Service necesita guardar o buscar un usuario, ¿a qué le habla? Si no hay nada en el medio, volvemos al problema de la Práctica 6.

La respuesta: una interfaz

Le habla a UsuarioDAO: un contrato que dice qué se puede pedir (alta, búsqueda, etc.) sin decir cómo se hace por adentro. UsuarioDAOImpl es quien implementa ese contrato con Hibernate y MySQL. El Service depende del contrato; la implementación concreta queda abajo, reemplazable.

El nombre técnico de esa solución

Eso se llama Principio de Inversión de Dependencias (DIP): los módulos de alto nivel (quien coordina: Resource y Service) no dependen de los de bajo nivel (UsuarioDAOImpl, Hibernate, MySQL). Ambos miran hacia una abstracción —en nuestro caso, la interfaz UsuarioDAO.

Antes (Práctica 6)

Alto nivel dependía directo del bajo nivel: UsuarioResource conocía UsuarioDAOImpl. Cambiar la implementación obligaba a tocar la puerta HTTP.

Ahora (Entrega 4)

UsuarioService depende de UsuarioDAO. UsuarioDAOImpl implementa la interfaz. Se puede cambiar cómo se persiste sin tocar Resource ni la regla de capas.

Conexión con la diapositiva 2

DIP no es un tema nuevo aparte. Es la herramienta concreta que permite cumplir la regla de “qué sí y qué no puede saber cada capa”: el Resource conoce al Service, el Service conoce la interfaz del DAO, y nadie de arriba importa UsuarioDAOImpl.

Entrega 4 · 3 → DI
Entrega 4 · 4/13 · DI

Inyección de dependencias: alguien te pasa lo que necesitás

en vez de crear la dependencia adentro

DI es la forma concreta de cumplir DIP: en lugar de que el Resource cree el DAO a mano, alguien desde afuera le entrega la dependencia ya lista.

Tres formas de inyectar
a) Por constructor

Las dependencias se pasan al crear el objeto. Es la más recomendada en general: deja claro qué necesita la clase y facilita los tests.

b) Por campo (field injection)

La dependencia se declara en un campo y el contenedor la completa. Es la forma más corta de escribir con CDI y Jersey.

c) Por setter

Se entrega la dependencia con un método de asignación. Sirve sobre todo cuando la dependencia es opcional.

Cómo Weld elige qué entregar

Con @Inject, Weld busca un bean compatible con el tipo pedido. Si pedís una clase concreta (por ejemplo el Service), entrega el bean de esa clase. Si pedís una interfaz (por ejemplo el DAO de usuario), busca cuál bean la implementa; si hay una sola, la entrega automáticamente. Eso conecta los dos lados de la idea DIP de la diapositiva anterior: DIP pone la interfaz en el medio; Weld es quién conecta el lado que pide el contrato con el lado que lo implementa, sin que el alto nivel conozca la clase concreta.

Por qué elegimos field injection en esta entrega: con CDI y Jersey es la forma más corta de escribirlo, y es lo que pedía el práctico. La inyección por constructor sería más testeable; field injection es lo que aplicamos acá.

Entrega 4 · 4 → IoC
Entrega 4 · 5/13 · IoC

Inversión de control: ya no manejamos el ciclo de vida

quién crea, inyecta y destruye

En la diapositiva anterior vimos cómo Weld encuentra el bean correcto cuando alguien pide un tipo (clase concreta o interfaz). Eso es solo una parte de lo que hace: además de elegir la pieza correcta, también decide cuándo crearla y cuándo destruirla, cosas que antes hacía el programador a mano.

Antes

El programador decidía cuándo y cómo se creaba cada objeto: en qué momento nacería el DAO, con qué clase concreta, y en qué línea del código.

Esa decisión se repetía en cada lugar donde hacía falta esa pieza (o se centralizaba a mano en un Factory, pero igual la inventaba el programador).

Ahora

Weld es quien toma esa misma decisión: cuándo crear el objeto, cuándo entregárselo a quien lo pidió, y cuándo destruirlo.

El programador solo declara qué necesita con @Inject, sin decidir el momento: no elige cuándo nace ni cuándo muere la pieza.

Por qué se llama “inversión”

El control que antes estaba del lado del programador ahora está del lado del framework. Con la diapositiva anterior (DI) vimos que Weld sabe qué bean darte (según el tipo pedido: clase o interfaz); acá se ve que Weld también decide cuándo dártela y cuándo destruirla. Son dos preguntas distintas —qué pieza y en qué momento— resueltas por la misma pieza.

Entrega 4 · 5 → CDI
Entrega 4 · 6/13 · CDI y Weld (1/2)

Del “framework” al motor concreto

estándar · implementación · escaneo
La pregunta que queda de IoC

Dijimos que “el framework” decide crear, inyectar y destruir. Eso no es magia abstracta: hace falta un estándar de reglas (qué anotaciones existen y qué significan) y una herramienta concreta que las ejecute al arrancar y en cada petición.

CDI = el estándar

CDI es el contrato de Jakarta para inyección y ciclo de vida. Define anotaciones como @Inject, @RequestScoped, @ApplicationScoped, @Produces y @Disposes. Por sí solo no crea ni destruye nada: solo dice las reglas.

Weld = quien las cumple

Weld es la implementación concreta que usamos. Es quien de verdad lee esas anotaciones, crea los objetos, los inyecta y los destruye. Sin Weld, las anotaciones serían etiquetas sin efecto.

Cómo se entera Weld de qué clases administrar

Al arrancar, Weld recorre las clases del proyecto buscando cuáles tienen anotación de scope (@RequestScoped o @ApplicationScoped). A esas las registra como bean: objetos cuyo ciclo de vida gestiona él. Eso se habilita con beans.xml en modo bean-discovery-mode="annotated": “escaneá solo lo anotado”. Sin ese archivo, Weld no arranca y @Inject no funciona.

Por qué el Resource también tiene que ser bean

Jersey atiende HTTP, pero no inventa las dependencias solo. Para poder inyectarle el Service al Resource, esa clase tiene que pasar por Weld. El puente entre Jersey y CDI es jersey-cdi1x-servlet. Si el Resource no fuera bean, Jersey lo crearía a mano y lo que debería inyectarse quedaría vacío.

Puente a la siguiente diapositiva: ya sabemos quién es el motor y cómo registra beans. Falta ver cuánto dura cada bean (por petición o por toda la app) y cómo una fábrica permanente puede fabricar algo distinto en cada pedido.

Entrega 4 · 6 → scopes
Entrega 4 · 7/13 · CDI y Weld (2/2)

Cuánto dura cada bean (y la fábrica vs lo fabricado)

@RequestScoped · @ApplicationScoped · Producer
@RequestScoped — una instancia por petición

En un POST /api/usuarios, Weld crea para ese pedido un UsuarioResource, un UsuarioService, un UsuarioDAOImpl y el EntityManager de esa petición. En un pago, crea PagoResource, PagoService y los tres DAOs que coordina (PagoDAO, InscripcionCongresoDAO, UsuarioDAO), todos compartiendo el mismo EntityManager de esa petición puntual. Al terminar el pedido, todas esas instancias se destruyen juntas: no queda estado colgado para el próximo cliente.

@ApplicationScoped — una sola instancia para toda la app

Ejemplos: EntityManagerProducer y DocumentStorageService. Esos dos no necesitan renovarse en cada pedido porque no guardan datos de una petición particular: el Producer solo sabe cómo crear y cerrar EntityManagers; el servicio de documentos solo sabe guardar y leer PDFs en disco. Una instancia permanente alcanza para toda la vida de la aplicación.

¿No es contradictorio? Fábrica permanente, producto por petición

EntityManagerProducer es una clase única y permanente (@ApplicationScoped). Adentro tiene un método con @Produces que fabrica un EntityManager distinto por cada petición, y un método con @Disposes que lo destruye cuando esa petición termina. La fábrica es una sola; lo que fabrica es distinto cada vez. Por eso conviven @ApplicationScoped (la fábrica) y scope de request (el EntityManager producido) en el mismo mecanismo, sin contradicción.

Puente a la siguiente: ya se vio quién administra (Weld), qué reglas sigue (CDI) y cuánto dura cada bean (@RequestScoped / @ApplicationScoped). Falta ver cómo Weld decide qué bean entregar cuando se pide un tipo con @Inject (una clase concreta o una interfaz).

Entrega 4 · 7 → qué implementación
Entrega 4 · 8/13 · EntityManager

Qué implementación inyectar, y un EntityManager por petición

@Inject · @Produces · @Disposes
La pregunta que quedó abierta

Con @Inject, Weld busca un bean compatible con el tipo pedido: clase concreta (ej. UsuarioService) o interfaz (ej. DAO de usuario → UsuarioDAOImpl si es la única). El escaneo de scopes llena ese registro de beans.

¿Por qué un solo EntityManager por petición y no uno por DAO?

El problema — historia de un pago a medias

Imaginá que PagoService coordina tres DAOs y cada uno abre su propio EntityManager y su propia transacción. Primero el DAO de pago guarda el pago: todo bien, confirma y cierra. Después el DAO de inscripción guarda la inscripción: también bien, confirma y cierra. Al final el DAO de usuario falla (por ejemplo, un dato inválido). Los dos primeros ya quedaron confirmados en MySQL y no se pueden deshacer: hay un pago y una inscripción registrados, pero el resto de la operación no terminó. Quedó todo a medias. Lo que se perdió es la atomicidad: la garantía de que o se guarda todo junto, o no se guarda nada.

La solución: EntityManagerProducer

Con @Produces y scope de request, Weld crea un EntityManager al inicio de la petición y abre la transacción. Los tres DAOs del pago (PagoDAO, InscripcionCongresoDAO, UsuarioDAO) usan ese mismo EntityManager. Al terminar, @Disposes cierra el ciclo: si los tres funcionaron, hace commit de los tres juntos; si cualquiera falló, hace rollback de los tres juntos — y cierra el EntityManager. Así el pago no puede quedar a medias.

Puente: el Producer fabrica un EntityManager por petición, pero ¿quién deja lista la fábrica antes de que llegue el primer pedido? Eso no es un gancho de bean CDI: es el arranque de Tomcat. Siguiente diapositiva.

Entrega 4 · 8 → fábrica vs producto
Entrega 4 · 9/13 · Arranque JPA

Fábrica una vez, EntityManager por petición

JpaBootstrapListener · EMF · EM
¿Por qué no @PostConstruct / @PreDestroy?

Esos son ganchos de CDI, atados al ciclo de vida de un bean (@RequestScoped o @ApplicationScoped): corren cuando nace o muere ese bean. Acá hace falta algo que exista antes de que arranque cualquier bean y se cierre después de apagar todo el servidor. Tomcat ofrece su propio gancho: ServletContextListener, con contextInitialized al levantar y contextDestroyed al bajar. Eso es lo que usa JpaBootstrapListener, en vez del gancho de CDI.

EntityManagerFactory y EntityManager: suenan parecido, no son lo mismo

La EntityManagerFactory es pesada de armar: lee persistence.xml, prepara la conexión a MySQL, deja listo Hibernate. Se crea una sola vez para toda la vida del servidor: eso lo hace JpaBootstrapListener en contextInitialized, y la cierra en contextDestroyed.

El EntityManager es lo que esa fábrica produce: uno nuevo por cada petición HTTP. Eso lo hace EntityManagerProducer (@Produces / @Disposes), usando la fábrica que el listener ya dejó lista.

En una frase: JpaBootstrapListener arma la fábrica una sola vez; EntityManagerProducer usa esa fábrica para sacar un producto nuevo en cada petición (y destruirlo al terminar el pedido).

Entrega 4 · 9 → flujo A–C
Entrega 4 · 10/13 · Flujo (1/2)

POST /api/usuarios: de la red al Service

Fases A, B y C
Fase A · Cliente y Jersey (igual que Práctica 6)

Alguien completa el formulario de alta de usuario y lo envía. Llega POST /api/usuarios con JSON. Tomcat lo deriva al ServletContainer de Jersey (web.xml, rutas /api/*). Jersey enruta con @ApplicationPath("/api"), @Path("/usuarios") y @POST. Jackson convierte el JSON en un objeto Usuario. Para llamar a alta(...), Jersey necesita un bean CDI, no un new a mano.

Fase B · Weld crea e inyecta (nuevo en E4)

El servidor arma el equipo que va a atender este pedido puntual. Gracias a jersey-cdi1x-servlet (el puente Jersey–CDI que ya vimos), Weld (el motor CDI) entrega un UsuarioResource @RequestScoped (una instancia solo para esta petición). Ve @Inject UsuarioService y crea el Service; ve @Inject UsuarioDAO y crea UsuarioDAOImpl (clase concreta o interfaz: Weld elige el bean compatible, como en DI). El DAO pide un EntityManager: Weld llama al @Produces de EntityManagerProducer (la fábrica permanente que saca un EM por petición), abre la transacción, y ese mismo EntityManager lo comparten Resource, Service y DAO.

Fase C · Presentación delega en Aplicación

Antes de guardar, alguien tiene que revisar si el pedido tiene sentido. UsuarioResource.alta(...) no llama al DAO. Llama a usuarioService.alta(usuario) (el Resource solo conoce al Service de al lado, regla de capas). El Service valida: email no repetido, email en minúsculas, rol PARTICIPANTE por defecto. Si el email ya existe, lanza NegocioException.

Entrega 4 · 10 → flujo D–E
Entrega 4 · 11/13 · Flujo (2/2)

Del DAO a MySQL: error 400 o éxito 201

Fases D y E
Fase D · Aplicación, infraestructura y MySQL

Ya se validó que el email es válido; ahora hay que guardarlo de verdad en la base. UsuarioService llama a usuarioDAO.alta(usuario). En modo CDI, AbstractJpaDAO hace persist sobre el EntityManager inyectado (el mismo de esta petición; no abre otra transacción — atomicidad del Producer). Hibernate lee @Entity / @Table y arma el INSERT. MySQL asigna el id; el objeto en memoria ya lo tiene.

Fase E · Dos salidas posibles

Acá el sistema se pregunta: ¿el email que mandaron ya existía o no? Según la respuesta, el camino se bifurca.

Error de negocio

El email ya estaba: se rechaza el alta. NegocioException sube hasta Jersey. NegocioExceptionMapper (ExceptionMapper: convierte la excepción en respuesta HTTP) responde HTTP 400 con {"error":"..."}. @Disposes hace rollback y cierra el EntityManager: no queda fila a medias.

Éxito

El email era nuevo: se confirma el alta y se avisa al cliente. El Resource convierte el resultado a UsuarioDTO (la versión sin password que vimos en Arquitectura), responde HTTP 201 con header Location, Jackson arma el JSON, y @Disposes hace commit y cierra.

Detalle de coloquio

El Resource no arma a mano el JSON de error: lanza la excepción correcta y el ExceptionMapper hace el resto. Misma idea para 404 con NotFoundExceptionMapper.

Entrega 4 · 11 → Swagger
Entrega 4 · 12/13 · Swagger

Probar la API sin inventar otro camino

OpenAPI · misma petición real
Qué es

Swagger es la interfaz visual para probar los mismos endpoints que curl o Postman. No ejecuta lógica de negocio propia: dispara el flujo HTTP real (Tomcat, Jersey, Weld, Service, DAO, MySQL) y muestra el código de respuesta. La página está en /swagger-ui/ (swagger-ui/index.html).

Qué hace cada anotación en la pantalla
@Tag

Agrupa endpoints bajo un nombre visible (Usuarios, Trabajos, Pagos…).

@Operation

Describe qué hace ese endpoint: es el título del formulario “Try it out”.

@ApiResponse

Documenta códigos HTTP posibles (201, 400, 404…) antes de probar.

Cómo se arma solo

OpenApiResource lee las anotaciones y genera GET /api/openapi.json. Swagger UI lee ese JSON y dibuja los formularios sola. Un endpoint nuevo bien anotado aparece solo en la pantalla.

Cómo comprobamos que persistió

En la misma página de Swagger: después del POST (“Try it out” → Execute), un GET del mismo recurso. Si volvió el JSON, persistió. Si fue 400, el GET no muestra esa fila. Sin phpMyAdmin.

Bloque 4 · Reflexión

Qué nos llevamos

2 min
Las capas no son burocracia

Cuando cambiamos el frontend entero de React a Angular, el backend no se tocó. Ese día entendimos para qué sirve separar en capas.

El modelo de datos es la decisión más cara

Convertir la asignación de evaluadores en una entidad propia costó una tarde en la Entrega 2 y nos ahorró semanas en la 4 y la 6.

Configurable le gana a hardcodeado

Etapas, catálogos, aranceles y cupos los define el organizador. Si estuvieran en el código, cada edición del congreso pediría un despliegue.

Desplegar temprano y seguido

Tener CI desde la Entrega 3 convirtió “anda en mi máquina” en un problema de cinco minutos en vez de una crisis la noche anterior a entregar.

Programar en equipo es coordinar, no repartir

Git resuelve los archivos; las decisiones sobre el dominio compartido hay que conversarlas antes de escribirlas.

Si tuviéramos una entrega más

Hash de contraseñas con BCrypt, autorización declarativa con @RolesAllowed, Bean Validation en los DTOs y pruebas automatizadas dentro del pipeline.
